# 2026-10-19 — LFXV2-2665: Performance Max create at Google Ads API v23

**Fix** — Performance Max creation had never succeeded against the live account. A prod dispatch
on 2026-10-16 created the campaign budget and then lost the campaign to HTTP 400, twice, leaving a
paid budget orphaned each time. Two blockers were stacked, and only the first was visible.

**The probes.** Three `validateOnly` `campaigns:mutate` calls at v23 against the real account on
2026-10-16, the same payload each time bar one field. A, B and D are the probe scripts' own
labels, kept so this entry and `PMAX_ACTION_PLAN` §2 name the same probes; these three are the
ones the conclusion rests on.

| Probe | Payload | Result |
| --- | --- | --- |
| A | the prod payload as sent | 400 INVALID_ARGUMENT — Unknown name `"urlExpansionOptOut"` at `'operations[0].create'` |
| B | A minus `urlExpansionOptOut` | 400 `REQUIRED_BUSINESS_NAME_ASSET_NOT_LINKED` + `REQUIRED_LOGO_ASSET_NOT_LINKED` |
| D | B plus `brandGuidelinesEnabled: false` | VALIDATED OK |

**Blocker 1 — `url_expansion_opt_out` was removed outright at v23**, on the campaign and the asset
group alike; `googleAdsFields:search` for `%url_expansion%` now returns only the reporting view
`final_url_expansion_asset_view`. The field is gone from `performanceMaxCampaignCreate`, and
`pmax_test.go` lists `urlExpansionOptOut` among the shapes that must never appear on this channel.
That assertion is not decoration: Google rejects an unknown field AFTER the budget mutate has
committed, so re-adding it does not fail safe — it orphans a paid budget, which is exactly what it
did on 2026-10-16.

**The risk the removed field covered did not go with it.** Final-URL expansion is now ON by
default and can only be turned off in the Google Ads UI, per campaign, by hand. Without it
Performance Max crawls the site, generates its own landing pages, and spends the event's budget on
URLs carrying none of the UTM attribution the data pipeline parses back out. **This is an operator
step after every Performance Max create, and nothing in the API can enforce it.** So it is
surfaced where the operator actually looks: `CreatePerformanceMaxCampaign` puts an
`ACTION REQUIRED:` entry in the result's `Steps` on **every path that hands back a campaign that
exists**, not beside the closing step at the end. Placement is the whole point, and the test of
it is not "where in the cascade" but "does this return hand back something billable":

- **Confirmed.** The step is appended immediately after the campaign create is confirmed, so every
  later return — geo, criteria, context-cancelled, asset group — carries it.
- **2xx with an unusable resource name.** `firstResourceName` and `validateCampaignResource` fail
  *after* `campaigns:mutate` answered 2xx. The campaign was created; only its name came back
  unusable, so the result carries no `CampaignID` and these `Steps` are the one thing saying a
  billable campaign is out there. They get the same unhedged sentence.
- **`DUPLICATE_CAMPAIGN_NAME` and an ambiguous outcome.** Hedged wording — "if that campaign
  exists" — because both already send the operator to the Google Ads UI to check, and a name that
  is taken means some earlier attempt created the campaign and may itself have died before
  printing this step.
- **A duplicate BUDGET name.** The same hedged wording, one mutate earlier. The budget name is
  this client's idempotency key, so a re-dispatch of the same brief on this channel is rejected at
  `campaignBudgets:mutate` and `campaigns:mutate` is never attempted — but the attempt that
  created that budget may have got past Step 2, leaving a campaign billing with expansion on. The
  other two budget arms stay silent: there the budget itself is the open question and the campaign
  create provably was never reached.
- **A definite non-ambiguous error** is the one arm that stays silent: no campaign was created.

`internal/dispatch/googleads.go` retains and persists the claim on any non-nil result, so each of
these puts an operator in front of exactly these `Steps`, finishing the work by hand in the Google
Ads UI and launching from there. At the end of the cascade the warning reached only the success
path, which is the operator least likely to need it. Five cases are asserted — the happy path, a
failed asset-group link mutate, a 2xx with no resource name, a duplicate campaign name, and a
duplicate budget name (whose test also fails if `campaigns:mutate` is reached) — so a refactor
that dropped the step, or moved it back to the end, would otherwise stay invisible until a
campaign had already overspent.

**Blocker 2 — the account has Brand Guidelines on.** A Performance Max campaign created under it
must link a BUSINESS_NAME and a square LOGO as CAMPAIGN assets — Google's error text says
"linked as a CampaignAsset". The gap is not that this service cannot build those two assets:
`pmax_creative.go` builds both, with the square logo's geometry bound already enforced. The gap is
where and when — they are linked as ASSET-GROUP assets at Step 5, after the Step 2 campaign
create, so satisfying Brand Guidelines needs a campaign-level `campaignAssets:mutate` link AND a
reordering of the cascade so the assets exist before the campaign does. Adding the link step alone
would still run too late. `brandGuidelinesEnabled` is sent explicitly as `false`, with no
`omitempty` guarding it — the whole point is that `false` reaches Google, and an omitted field
would take the account's own setting instead and put the create straight back on probe B's 400.
The test asserts the literal `"brandGuidelinesEnabled":false` rather than merely the field's
presence, so an `omitempty` added later fails loudly instead of silently restoring the bug.
Linking the assets is the better answer and is what should replace this field when the media work
lands. Treat the setting as decided at create time: Brand Guidelines is not an ordinary mutable
campaign field, and nothing here has established what re-enabling it on an existing campaign
costs — so the code says so rather than promising a UI toggle it has never exercised.

**Correcting an earlier entry.** `2026-10-05-LFXV2-2665-google-performance-max.md` describes the
shell as sending `urlExpansionOptOut: true` "so it serves the final URL it was given". That was
true of the code when it was written and is no longer true of the API or the code. Log entries are
never edited, so the correction is recorded here;
`docs/knowledge/code/internal-platform-googleads.md` and its `index.md` bullet have been updated
to match the shipped payload.
