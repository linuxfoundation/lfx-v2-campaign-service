# 2026-10-19 — LFXV2-2665: Performance Max create at Google Ads API v23

**Fix** — Performance Max creation had never succeeded against the live account. A prod dispatch
on 2026-10-16 created the campaign budget and then lost the campaign to HTTP 400, twice, leaving a
paid budget orphaned each time. Two blockers were stacked, and only the first was visible.

**The probes.** `validateOnly` `campaigns:mutate` calls at v23 against the real account, the same
payload each time bar one field, so nothing was ever created. A, B and D ran on 2026-10-16; E and
F on 2026-10-19. A, B and D are the probe scripts' own labels, kept so this entry and
`PMAX_ACTION_PLAN` §2 name the same probes.

| Probe | Payload | Result |
| --- | --- | --- |
| A | the prod payload as sent | 400 INVALID_ARGUMENT — Unknown name `"urlExpansionOptOut"` at `'operations[0].create'` |
| B | A minus `urlExpansionOptOut` | 400 `REQUIRED_BUSINESS_NAME_ASSET_NOT_LINKED` + `REQUIRED_LOGO_ASSET_NOT_LINKED` |
| D | B plus `brandGuidelinesEnabled: false` | VALIDATED OK |
| E | D plus `assetAutomationSettings: [{FINAL_URL_EXPANSION_TEXT_ASSET_AUTOMATION, OPTED_OUT}]` | VALIDATED OK |
| F | E with a bogus `assetAutomationType` | 400 naming `AssetAutomationTypeEnum.AssetAutomationType` |

E is the one that matters, and F is why E can be trusted: a string Google ignored would have
validated just as cleanly, so the bogus-value run proves the field is read and the value is a real
member of that enum. A `googleAdsFields:search` for `%asset_automation%` on the same day returns
`campaign.asset_automation_settings`
(`google.ads.googleads.v23.resources.Campaign.AssetAutomationSetting`).

**Blocker 1 — `url_expansion_opt_out` was removed outright at v23**, on the campaign and the asset
group alike; `googleAdsFields:search` for `%url_expansion%` now returns only the reporting view
`final_url_expansion_asset_view`. The field is gone from `performanceMaxCampaignCreate`, and
`pmax_test.go` lists `urlExpansionOptOut` among the shapes that must never appear on this channel.
That assertion is not decoration: Google rejects an unknown field AFTER the budget mutate has
committed, so re-adding it does not fail safe — it orphans a paid budget, which is exactly what it
did on 2026-10-16.

**The risk the removed field covered did not go with it — and neither did the control.** Left to
Google's default, Performance Max crawls the site, generates its own landing pages, and spends the
event's budget on URLs carrying none of the UTM attribution the data pipeline parses back out:
that default is what `urlExpansionOptOut: true` existed to override, and nothing about v23 says it
changed. What v23 removed is the FIELD, not the control: it moved into
`campaign.asset_automation_settings`, which is settable at CREATE and supported on this channel —
probe E. So the payload now carries one entry,
`FINAL_URL_EXPANSION_TEXT_ASSET_AUTOMATION` / `OPTED_OUT`, and the opt-out ships with the campaign
instead of waiting on an operator remembering to do it in the UI.

This is not a like-for-like rename of `urlExpansionOptOut` and must not be read as one. The entry
opts out of ONE asset-automation type, and Google may add others that this payload then leaves at
their default. It is sent as a one-element slice literal without `omitempty`, so an empty slice can
never be the thing that silently restores the default — the same reasoning as
`brandGuidelinesEnabled` below.

**What the `Steps` now say, and to whom.** `CreatePerformanceMaxCampaign` still writes a
final-URL-expansion sentence on **every path that hands back a campaign that exists**, not beside
the closing step at the end — but there are now two sentences, and which one a path gets turns on
whose campaign it is talking about:

- **Confirmed**, and **2xx with an unusable resource name**, and every later return — geo,
  criteria, context-cancelled, asset group — get the informational step: this request created the
  campaign, so the opt-out went out with it. In the unusable-name case `firstResourceName` and
  `validateCampaignResource` fail *after* `campaigns:mutate` answered 2xx, so the result carries no
  `CampaignID` and these `Steps` are the one thing saying a billable campaign is out there at all.
- **`DUPLICATE_CAMPAIGN_NAME`, an ambiguous outcome, and a duplicate BUDGET name** keep an
  `ACTION REQUIRED:` and keep the hedge — "if that campaign exists". The campaign these three
  describe was created by some EARLIER attempt, which may predate this service sending the setting
  at all; the two prod dispatches of 2026-10-16 are exactly that. The budget case is one mutate
  earlier: the budget name is this client's idempotency key, so a re-dispatch of the same brief is
  rejected at `campaignBudgets:mutate` and `campaigns:mutate` is never attempted — but the attempt
  that created that budget may have got past Step 2. The other two budget arms stay silent: there
  the budget itself is the open question and the campaign create provably was never reached.
- **A definite non-ambiguous error** is the one arm that stays silent: no campaign was created.

`internal/dispatch/googleads.go` retains and persists the claim on any non-nil result, so each of
these puts an operator in front of exactly these `Steps`, finishing the work by hand in the Google
Ads UI and launching from there. At the end of the cascade the sentence reached only the success
path, which is the operator least likely to need it. Five cases are asserted — the happy path, a
failed asset-group link mutate, a 2xx with no resource name, a duplicate campaign name, and a
duplicate budget name (whose test also fails if `campaigns:mutate` is reached). Each asserts the
exact const and fails if the OTHER sentence appears, because a substring match would pass on a
path telling the operator to go fix a campaign this request already opted out. The campaign-shape
test pins the literal `"assetAutomationType"` and `"assetAutomationStatus"` values in the captured
body, and keeps `urlExpansionOptOut` on the list of shapes that must never appear.

**Blocker 2 — the account has Brand Guidelines on.** A Performance Max campaign created under it
must link a BUSINESS_NAME and a square LOGO as CAMPAIGN assets — Google's error text says
"linked as a CampaignAsset". The gap is not that this service cannot build those two assets:
`pmax_creative.go` builds both, with the square logo's geometry bound already enforced. The gap is
where and when — they are linked as ASSET-GROUP assets at Step 5, after the Step 2 campaign
create, so satisfying Brand Guidelines needs a campaign-level `campaignAssets:mutate` link AND a
reordering of the cascade so the assets exist before the campaign does. Adding the link step alone
would still run too late. `brandGuidelinesEnabled` is sent explicitly as `false`, with no
`omitempty` guarding it — the whole point is that `false` reaches Google, and an omitted field
would take the account's own setting instead and put the create straight back on probe B's 400.
The test asserts the literal `"brandGuidelinesEnabled":false` rather than merely the field's
presence, so an `omitempty` added later fails loudly instead of silently restoring the bug.
Linking the assets is the better answer and is what should replace this field when the media work
lands. Treat the setting as decided at create time: Brand Guidelines is not an ordinary mutable
campaign field, and nothing here has established what re-enabling it on an existing campaign
costs — so the code says so rather than promising a UI toggle it has never exercised.

**Correcting an earlier entry.** `2026-10-05-LFXV2-2665-google-performance-max.md` describes the
shell as sending `urlExpansionOptOut: true` "so it serves the final URL it was given". That was
true of the code when it was written and is no longer true of the API or the code. Log entries are
never edited, so the correction is recorded here;
`docs/knowledge/code/internal-platform-googleads.md` and its `index.md` bullet have been updated
to match the shipped payload.
