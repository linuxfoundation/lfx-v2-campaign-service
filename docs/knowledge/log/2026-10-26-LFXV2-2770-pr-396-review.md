# 2026-10-26 — PR #396 review: resolved exclusions checked and fingerprinted (LFXV2-2770)

**Fix** — bot review findings on the standing suppression lists.

- `resolveSuppressions` takes the send's inclusion ids and refuses, with
  `audience.ExclusionOverlapError` (400 naming the list), a standing or registrants list that is
  also an inclusion. It reads both standing lists by name before any create or growth, and checks
  the final ids again, so compose creates no master and attach records nothing. Before, the input
  overlap check could not see the substituted standing list or the added registrants list: attach
  recorded an audience dispatch refuses, and compose could build a master excluding its own
  inclusion branch.
- `ComposeMaster` fingerprints the RESOLVED exclusion ids instead of the requested ones, so a
  project on a shared portal, or a recreated standing or registrants list, no longer reuses a
  master that excludes different lists than the response reports.
- A refused standing-list create that is still not found is looked up across object types
  (`hubspot.Client.SearchListsAnyType`), and a non-contact list holding the name becomes the named
  409 instead of a 500. Whether HubSpot's list search returns every object type when
  `objectTypeId` is omitted is from its API reference, not yet confirmed live.
- Tests: `audience_suppression_test.go` (overlap on attach and compose, two projects on one portal,
  a recreated standing list, a non-contact name holder), `lists_test.go`,
  `audience_attach_existing_test.go`. See [internal/dispatch](../code/internal-dispatch.md).
