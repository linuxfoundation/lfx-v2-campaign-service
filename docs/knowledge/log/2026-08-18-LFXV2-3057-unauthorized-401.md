# 2026-08-18 — LFXV2-3057 authentication failures answer 401, not 400

**Update** — a bearer token this service refuses now answers **`401 Unauthorized`** with a
`WWW-Authenticate: Bearer` challenge (RFC 9110 §15.5.2), on every method of all three
authenticated services. It answered `400` since LFXV2-3053, when `JWTAuth` began verifying
tokens in-process against Heimdall's JWKS.

**Why the status was wrong on the wire.** `400` means the request was malformed; an
unauthenticated request is well-formed and the credential is what needs replacing. Two
things followed from conflating them. A client could not distinguish "token expired,
refresh and retry" from "payload invalid, do not retry" — opposite handling, and the
refresh is exactly the retry a `401` is supposed to trigger. And status-based alerting
counted every auth failure as a client payload error, so an expired credential or a JWKS
outage surfaced as a spike in malformed requests rather than as an auth incident.

**`UnauthorizedError` is a new design type, not a remapped `BadRequestError`.** Goa keys a
method's error encoder on the error NAME, so one type under two names would still need two
`Error(...)` declarations and one name cannot carry two statuses. `BadRequest` stays
declared everywhere alongside it — it is still the status for payload and path-parameter
validation, which even the bodyless reads reach through the generated decoder (the
`create-*` routes constrain `project_id` to a slug `Pattern`). Dropping it because auth
moved off it would have turned those into `500`s.

**The challenge is a field of the error, and that is the only way it reaches the wire.**
Goa's Response-level `Header()` maps an *attribute* of the error type onto a response
header; it has no form that emits a fixed string. So `www_authenticate` is a `Required`
attribute on `UnauthorizedError`, mapped in `connectionAuthErrorResponses` and
`briefErrorResponses`, and filled from one shared `bearerChallenge` constant in
`internal/service/auth.go`. Delete the `Header()` mapping and the field silently
serializes into the JSON body instead: the status is still `401`, every encoder still has
its `Unauthorized` case, and the response violates the RFC with nothing failing.
`TestEveryConnectionUnauthorizedEncoderSetsTheChallenge` reads the generated encoders and
counts challenge-setting sites against `Unauthorized` cases, which is what catches that.

**The challenge is the bare scheme** — no `realm`, no `error="invalid_token"`. Both are
optional, and an `error` code names WHICH check failed, which is precisely the
reason-specific signal the opaque message exists to keep off the wire.

**The rejection message did not change and must not.** The status now says which KIND of
thing is wrong; it still says nothing about which check failed. Expired, wrongly signed,
and accepted-without-naming-a-principal remain one indistinguishable answer, because a
specific reason only tells an attacker what to fix next.
`TestAuthenticate_RejectionMessagesAreOpaque` still pins that at the guard, and it still
binds — reverting the message to include the verifier's error fails it.
`TestJWTAuth_UnauthorizedMessageIsOpaqueAcrossServices` adds the wire-level half the guard
test cannot see: it calls `JWTAuth` on all three services and compares message AND
challenge across two different token-side reasons, so a service that enriched the body on
its way out is caught.

**The 503 split is untouched.** `authenticate`'s `unavailable bool` still separates "this
service could not PERFORM the check" — no verifier wired, or `domain.ErrKeyUnavailable`
from a JWKS outage — from "the token was refused". The first is still `503`; only the
second moved from `400` to `401`. Answering `401` for a JWKS outage would send a caller to
refresh a credential that was never the problem.

**Blast radius outside this repo: none found.** The ticket claimed `lfx-self-serve` does
not call campaign-service at all; that is now false — `campaign-service.service.ts` routes
brief save/load/find/replace, campaign create (LFXV2-3195) and the status toggle
(ss#1581) through it. But no consumer branches on `400` for auth. The campaign paths test
`statusCode >= 400 && < 500` (a range `401` was already inside), and the three exact-status
checks are `404`, `412` and `428`. The BFF's status table already maps `401` to
"Authentication required. Please log in and try again.", so the user-visible message
improves; a poll-path test already exercises `401` explicitly. Nothing there needed a
coordinated change.
