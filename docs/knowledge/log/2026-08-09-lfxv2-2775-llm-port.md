# 2026-08-09 — The service can call a model (LFXV2-2775, part 1 of 2)

**Update** — `internal/platform/llm` gives campaign-service its first route to an LLM: the LF
LiteLLM proxy's OpenAI-compatible `/chat/completions`, reached through an injected proxy URL and
key. No caller uses it yet; the email-copy generation that does lands next. The design decisions
and their reasoning live in [internal/platform/llm](../code/internal-platform-llm.md); this
entry records only what a reader of that page could not infer.

**Why a port before a feature, given that an unreferenced package secures nothing.** The
LFXV2-3053 entry argued the opposite case — package-first was refused there because an unwired
verification package passes every gate and leaves the hole open. The distinction is what
"unwired" costs. A verifier nobody calls means requests go unverified; a model client nobody
calls means no copy is generated, which is exactly today's behaviour. Nothing regresses while
this sits alone, and splitting it is what keeps both halves under the line-count cap with their
tests intact. The commitment that makes it honest: the consumer is the very next PR, and until
it lands the chart's `AI_*` values do nothing.

**Three properties failed at least once while being written, so each has a test proven binding
by reverting the fix.** Redirect refusal did not survive client injection — `WithHTTPClient`
replaced the client wholesale and silently discarded `CheckRedirect`, and injection is the
ordinary case since it exists to supply a transport. Transport-error rebuilding leaks on all six
cause classes when disabled, caught only because the test walks **every** layer through
`errors.Unwrap` rather than the outermost `Error()`. And removing the 429 drain takes the
connection count the server observes from 1 to 2.

**The chart wiring is not optional bookkeeping.** `SNOWFLAKE_*` shipped read-by-code and
absent-from-chart once: nothing failed, the warehouse lookup was simply disabled everywhere, and
every audience recorded "no past editions" — which reads as "first-time event", not "feature not
wired". `TestEveryConfiguredEnvVarIsWiredInTheChart` now covers `AI_PROXY_URL`, `AI_API_KEY` and
`AI_MODEL` automatically, since it derives its list from `pkg/constants`.

## Review round: normalise at construction, and print the AI settings rather than hide them

**Trimming for the emptiness check but storing the untrimmed value is worse than not trimming
at all.** `NewClient` validated `strings.TrimSpace(cfg.ProxyURL) == ""` and then kept whatever
arrived. These values come from Kubernetes secrets, where a trailing newline is the single most
common way a value is malformed, and each field carries it differently: a key ending in `"\n"`
builds an `Authorization` header Go's transport rejects outright as an invalid header value, and
a proxy URL with surrounding space no longer parses as the URL it looks like. Both then surface
at generation time as a request failure rather than as the misconfiguration they are — which is
precisely the failure mode constructing eagerly was meant to eliminate. `NewClient` now
normalises **and stores** `ProxyURL`, `APIKey` and `Model`, matching the hubspot/meta/twitter
clients. `Complete` deliberately does NOT re-trim: `NewClient` is the only writer of `cfg`, so
re-trimming would imply the field might still arrive padded and quietly weaken the invariant.
Both new tests assert on the wire (`Bearer <key>` exactly, `model` exactly), and the trim-only
form fails the first with `net/url: invalid control character in URL`.

**`Config.String()` omitted the AI settings entirely, which is log-safe and diagnostically
useless.** Omission answers nothing about the question an operator actually has — "why did copy
generation not run?" — which is answered by knowing *whether* a proxy and key are configured.
`AIProxyURL` and `AIModel` now print verbatim (neither is a secret) and `AIAPIKey` goes through
`redactSecret`, which renders `""` for unset and `xxxxx` for present: exactly the bit that is
needed, and nothing more. The `TestConfigString_RedactsSecrets` fixture carries all three so the
redaction and the survival of the two non-secrets are both pinned.

**Two doc claims were false and are corrected.** `internal-platform-llm.md` said all three
`AI_*` values were wired as optional secret refs; `AI_MODEL` is a plain `value: ''`, because a
model id is not a credential and empty is a meaningful default. And the `AI_*` group was missing
from both `kubernetes/deployment.md` and `pkg-constants.md` — the two pages a reader consults to
learn what the chart injects and what the service reads. The chart parity test cannot catch a
documentation omission; only reading for it can.

## Review round: a present proxy URL is not a usable one, and two index bullets went stale

**`NewClient` accepted any non-empty `AI_PROXY_URL`.** The doc comment claims a deployment
without a model wired is discovered once, at construction — but the check was emptiness only, so
`localhost:4000` passed. `url.Parse` accepts that string, reading `localhost` as the SCHEME, and
`http.NewRequest` then refuses it on every single generation: a one-line deployment mistake
reading as a recurring transport failure, which is the precise outcome constructing eagerly
exists to prevent. Construction now requires an absolute URL with an `http`/`https` scheme and a
host, and builds the `/chat/completions` endpoint once from the validated value, so requests
cannot use a form nothing checked.

`ErrInvalidProxyURL` wraps `ErrNotConfigured` rather than standing alone. Every caller degrades
on that sentinel, and an unusable proxy is operationally the same fact as an absent one — a
separate sentinel would have silently stopped each of them degrading, turning a message
improvement into a behaviour change. The test asserts both `errors.Is` relations for that reason.
Removing the validation makes all six rejection cases pass a nil error.

**Both description edits from the previous round broke the index contract** (`CLAUDE.md` step 2):
`kubernetes/index.md` and `code/index.md` still carried the pre-edit descriptions for Deployment
and `pkg/constants`. Corrected to match their frontmatter verbatim. Worth noting the shape —
`okfvalidate` passed throughout, because bullet text drifting from frontmatter is not something
it checks; only reading for it catches this, which is exactly how it survived the first round.

## Review round: the proxy URL is not a secret-free field, and its rejection paths quoted it

Copilot's finding: `AI_PROXY_URL` is printed verbatim by `Config.String()` while URL userinfo
and query parameters can carry passwords or tokens, and `NewClient` accepts both.

Correct on the merits, and it survives the obvious objection. The reflex is "the proxy URL is an
endpoint, the credential is in `AI_API_KEY`" — but secret-free is a property of what an operator
typed into the field, not of the field. Both credential-bearing components are ordinary: Go's
transport turns `https://user:token@proxy/` into a Basic credential, and `?api-key=…` is a shape
several LiteLLM deployments document. `String()` is the form every config log line uses, so
printing raw makes the pod log the disclosure channel.

The fix is not symmetric across the two layers, which is the part worth recording.

`Config.String()` **redacts** — `redactAIProxyURL` rebuilds the value from scheme, host and path.
Not `[redacted]` wholesale: that follows `redactNATSURL`, not `redactDatabaseURL`, because the
one question this string answers is "is copy generation pointed at a proxy, and which one", and
masking answers neither. Two shapes mask anyway, both because nothing about them is known safe —
an unparseable value, and an opaque one (`mailto:u:p@host`) whose entire content lands in a field
this does not render. A missing `Host` is the tell for the second; `url.Parse` only separates
userinfo for an authority-form url.

`llm.NewClient` **rejects** — `ErrProxyURLNotABase`, wrapping `ErrInvalidProxyURL` so callers keep
degrading. Rejection beats redaction here for a reason that has nothing to do with secrets: the
endpoint is built by appending `/chat/completions`, so a value ending in `?x=1` or `#frag`
produces a path nobody wrote, accepted at startup and wrong on every generation — the same late
failure this constructor exists to remove. The disclosure argument then arrives independently: a
value that is refused never reaches `Config`, a log, or anything downstream that formats it.
Redacting at print time would have left the raw value live everywhere else.

**The half of the finding that was easy to miss: the rejection paths were themselves the leak.**
`url.Parse` returns a `*url.Error` whose `Error()` embeds the raw url verbatim, so
`fmt.Errorf("%w: %w", ErrInvalidProxyURL, perr)` — as idiomatic a line as exists in Go —
re-publishes the whole credential-bearing string into the startup log and into every error it
propagates through. The other branch quoted `cfg.ProxyURL` outright. Both now name the components
they JUDGED instead of the value they read: scheme and host, which `url.Parse` has already split
away from userinfo and query and which therefore cannot carry either. `parseCause` unwraps the
`*url.Error` to its bare cause. The class generalises past this file: **an error path that
rejects untrusted input is the path least entitled to quote it**, and wrapping the library error
is the default that gets it wrong.

Revert-verified all three: forwarding `perr` raw fails with the credential visible in the
assertion output; dropping the not-a-base case returns nil for every userinfo/query/fragment
input; printing `c.AIProxyURL` raw puts `sup3r-s3cret` in the formatted config.

## Round 3: unwrapping the parse error was only most of the fix

Copilot, on the fix from round 2: unwrapping `*url.Error` does not make every parser error
safe, because `net/url`'s causes quote the fragment of the input they choked on. Verified
against Go directly rather than reasoned about:

    https://litellm.internal:sk-secret   inner = invalid port ":sk-secret" after host
    https://x/%zz                        inner = invalid URL escape "%zz"

The first is the one that matters: with no `@`, a secret typed where a port belongs is read
as the port, and the credential is quoted by the *cause*, which the round-2 fix forwarded.
The wrapper was the visible half of the leak; the cause was the other half, and unwrapping
looked like a complete fix precisely because it removed the visible one.

So the branch now discards the cause and returns a message assembled from constants. Nothing
is lost: `url.Parse`'s causes are unexported types or plain strings, so `errors.Is`/`As`
reach nothing a caller could branch on, and the sentinel is what callers match. The operator
learns which variable is malformed, which is all they need to go and read it.

The generalisation, extending round 2's: **a redaction that removes a value's obvious carrier
has not necessarily removed the value.** A library error is a chain, and any layer of it may
quote the input — so the safe default for an error about untrusted input is to construct the
whole message, not to sanitise an inherited one. `TestNewClient_RejectionNeverEchoesTheRawURL`
carries the malformed-port shape specifically because it is the case that passes under
unwrapping and fails only under construction.

## Round 4: the scheme and the host are not safe either

Copilot came back on the same file with the case round 3's fix does not cover, and on a
second site round 3 never looked at. Both are right, and both are the same lesson arriving
one layer further out.

The bad-scheme branch quoted `u.Scheme` and `u.Host`, on a documented claim that those two
components are safe because `url.Parse` has already split userinfo and query into their own
fields. That claim is false. `url.Parse` decides where the DELIMITERS fall; it does not
validate what a component CONTAINS. A pasted `sk-secret:tok@litellm.internal` parses as an
opaque url whose scheme is the credential, `sk-secret://litellm.internal` parses cleanly with
a host, and `https://sk-secret/?k=v` puts it in the hostname on the not-a-base branch. Three
reachable shapes, three different fields, one mistake: reasoning about where a value came
from instead of about the fact that it is unvalidated.

So no branch quotes anything now. Each names the component it judged and stops. The
scheme and host checks were split apart so the operator still learns which one failed —
that information costs nothing and reproduces nothing.

The second site is `redactAIProxyURL` in `internal/infrastructure/config`, and it matters
more than the first because it runs EARLIER: `Config.String()` is what every startup log
line renders, before `llm.NewClient` gets the chance to reject anything. It masked an
unparseable value and an opaque one (no host), but treated every parseable scheme as safe —
so `sk-secret://host` would have been printed into the pod log verbatim. It now masks any
scheme that is not http or https.

One existing assertion had to be INVERTED rather than extended:
`TestNewClient_RejectsAProxyURLCarryingUserinfoOrQuery` required the error to name the host,
with a comment explaining that the host is "the one part that is safe AND useful." That test
was pinning the wrong belief in place. A test that encodes a refuted claim will keep the
defect alive through every future fix that respects it, which is the more expensive half of
this round.

**Generalisation, sharper than round 3's.** Round 3 said a redaction that removes a value's
obvious carrier has not necessarily removed the value. Round 4 says why that keeps happening:
the instinct is to ask *which field could hold a secret*, and the answer is always "the one I
was not thinking about." For a value being rejected, the only stable rule is that no part of
it is quoted — because the reason it is being rejected is precisely that nothing is known
about it.

## Round 5: the doc drift my own fix caused, and three exactness bugs

Copilot's review body carried six SUPPRESSED findings — none of them a review thread, so
`unresolved=0` on this PR while six items sat open. Four were documentation, three of those
created by rounds 3 and 4: `internal-platform-llm.md` and `kubernetes/deployment.md` both still
said `Config.String()` prints `AIProxyURL` verbatim, which stopped being true the moment
`redactAIProxyURL` landed. Worth naming the shape rather than just the instance: a security fix
that changes what a function DISCLOSES silently invalidates every sentence describing the old
disclosure, and those sentences are the ones an operator reads to decide whether a log line is
safe to paste into a ticket. The fourth was older — the deployment frontmatter and its index
bullet said all `AI_*` come from the secret, but `AI_MODEL` is a plain chart value, and telling
an operator to provision a model id as a secret is a real instruction to do the wrong thing.

The dated log entries are deliberately NOT edited. Round 1 recorded that the URL printed
verbatim, and that was true when written; rounds 3 and 4 in this same file supersede it. A log
that revises its own history stops being evidence of how the reasoning moved, which is the only
thing it is for.

The three code findings share one description: a defence that is approximately right.

`io.ReadAll(io.LimitReader(body, cap))` bounds memory correctly and detects truncation not at
all, because `LimitReader` ends with EOF rather than an error. The failure needs the prefix to
parse, which sounds unlikely until you notice that trailing whitespace is legal JSON — a
complete completion object plus padding, cut at the cap, is accepted as the whole answer. The
`cap+1` read is the entire difference between bounding a read and validating one.

`retryAfter` returned zero for anything unparseable, and zero is a real answer here: "back off
on our own schedule". For an all-digit value too large for a `Duration` that answer inverts the
server's instruction — it says wait effectively forever, and we heard nothing and retried
immediately. The comparison has to happen in SECONDS, before the multiply that overflows.

`Temperature` is `Config`'s only pointer, which is exactly why it was missed: `cfg` is copied by
value and every other field genuinely is a snapshot. "Safe for concurrent use" is a claim about
the whole stored config, and one pointer is enough to make it false.

**Generalisation.** Two of these three are the same bug wearing different clothes: a value that
cannot be represented (a body past the cap, a delay past `Duration`) got reduced to a
representable one that means something else — "complete body", "no header". Saturation is not a
detail of the parse; it is where the contract is decided. And a `Config` copied by value is only
a snapshot of its non-pointer fields, which is the sort of thing a reader verifies by looking at
the struct rather than at the assignment.

## Round 6: the path, and the third time I made the same mistake

`redactAIProxyURL` kept the path. A reviewer produced
`https://litellm.example.com/sup3r-s3cret/v1`, which parses cleanly, is not userinfo and is
not a query, and was therefore printed verbatim by `Config.String()` on the startup log path —
before `llm.NewClient` (which accepts a path) ever runs. Real, and now scheme-and-host only.

What is worth recording is not the fix but that this is the THIRD round of the same error.
Round 3 was the scheme (`localhost:sk-secret`). Round 4 was the host. Round 6 is the path.
Each time the reasoning was that `url.Parse` had already separated the dangerous components
into their own fields, so what remained was structurally safe — and each time that confused
where the DELIMITERS fall with what a component CONTAINS. `url.Parse` is a tokenizer. It tells
you which bytes are the path; it has no opinion about whether those bytes are a token.

The rule that survives all three rounds is narrower than the one I kept re-deriving:
**a component is reproduced only when it is BOTH structurally incapable of holding a secret
AND load-bearing for the diagnosis.** The path fails on both counts — it can hold anything,
and "which proxy" is answered by the host. That rule is now written into
`docs/reviews/knowledge-base/credentials-and-untrusted-text.md` rather than only into the
config doc, because the place it needs to be applied next is the next redactor, not this one.

The three docs describing the old contract (`internal-infrastructure-config.md`,
`internal-platform-llm.md`, `kubernetes/deployment.md`) are updated. The round-1 entry above
still says "scheme, host and path"; that was true when written and is superseded here rather
than edited, because a log that revises its own history stops being evidence of how the
reasoning moved — which, on this bug, is the only useful thing it records.

## Round 7: the host was the last component still reproducing operator input

Copilot, on `internal/infrastructure/config/config.go:366`: `u.Host` is untrusted and can
itself be a pasted credential — `AI_PROXY_URL=https://sup3r-s3cret/` passes every check the
function makes and `Config.String()` logs the token verbatim.

Real, and the fourth appearance of one class. Rounds 3, 6 and now 7 are the same error about
three different components: the scheme (`sk-secret:foo`), the path
(`https://proxy/sk-secret/v1`), and the host. Each time the surviving component was defended
as "structurally safe", and each time that turned out to mean "url.Parse put it in this
field" — a statement about where the delimiters fall, not about what the component contains.
A host is free-form operator input exactly as a path is.

`redactAIProxyURL` now returns `u.Scheme + "://xxxxx"`. The scheme survives only because it
is compared against the literals `http` and `https` BEFORE it is printed, so what reaches the
log is one of two constants this function chose; an unrecognised scheme still masks
wholesale, since that is precisely the case where the scheme may be the secret. The
diagnostic loss is small and the remaining answer is the operational one: `https://xxxxx`
says copy generation is pointed at a proxy over TLS, and an operator who needs the exact host
has the deployment manifest.

The test suite gained a PROPERTY rather than another fixture:
`TestRedactAIProxyURL_ReproducesNothingButTheScheme` asserts that for any http(s) input the
output is drawn entirely from constants. That is what stops a round 8 — a future component
judged "structurally safe" fails there without anyone having to imagine its fixture first.

Docs updated: `internal-infrastructure-config.md`, `internal-platform-llm.md`,
`kubernetes/deployment.md`, and the review knowledge base entry, which now records the
sharper form of the rule: a component is safe to print only when the code compares it against
a constant before printing it.
