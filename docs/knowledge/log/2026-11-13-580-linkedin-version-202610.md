# 2026-11-13 — #580 LinkedIn-Version 202602 → 202610

**Update** — `internal/platform/linkedin` now sends `LinkedIn-Version: 202610` instead of
`202602`. The version is still named once (`apiVersion`, `config.go`); no env override was
added, because no platform client in this repo wires its API version from the environment
(the Google Ads and X `WithAPIVersion` options are test-only seams). The header test now pins
the literal `202610`, so a future bump has to touch the test as well as the constant.

## Why 202610

- **202610 is the latest version** LinkedIn publishes ("Latest Version: October 2026, 202610",
  [Versioning](https://learn.microsoft.com/en-us/linkedin/marketing/versioning?view=li-lms-2026-10)),
  supported until **October 15, 2027**.
- **202602 sunsets February 15, 2027** (API Migration Status table,
  [Migrations](https://learn.microsoft.com/en-us/linkedin/marketing/integrations/migrations?view=li-lms-2026-10)).
  LinkedIn supports each monthly version for at least a year, and a request carrying a sunset
  version gets an error, not a fallback.
- The #552/#557/#585 targeting, picker and conversion shapes were written against the
  li-lms-2026-10 docs. Sending 202602 meant the client ran against a different contract from
  the one its newest code was written to.

## Audit: Recent Changes 202603..202610 against the endpoints the client calls

Source: [Recent Changes](https://learn.microsoft.com/en-us/linkedin/marketing/integrations/recent-changes?view=li-lms-2026-10),
the sections from "October 2026 - Version 202610" down to the "February 2026 - Version 202602"
heading. Each change below is either additive, or applies to an API this package does not call.

| Version | Change | Our exposure |
| --- | --- | --- |
| 202610 | `/creatives` read responses may return `content.standardUpdateAd` / `content.videoAd` (`reference`, `contentAuthor`) instead of `content.reference`; create unchanged | None. The creatives finder (`q=criteria`, status cascade) decodes only id/status, never `content`. Create still sends `content.reference`, which the docs keep for create |
| 202610 | `/creatives` read-only `metadata` field, returned only on request | None. The paging envelope `metadata.nextPageToken` is a separate top-level field (the docs say so explicitly) |
| 202610 | `/adAnalytics` adds `memberFollows`, `memberProfileClicks` | Additive; we request explicit `fields` |
| 202610 (effective 202611, and on all versions after Dec 15, 2026) | `/adPublisherRestrictions` requires `surface` (`LAN`/`CTV`); campaigns may only use publisher lists whose placement type matches | None. No publisher lists are created or attached, and campaigns are created with `offsiteDeliveryEnabled: false` |
| 202609 | `adAnalytics` pivot `MEMBER_DESIGNATED_MARKET_AREA`; Conversions API 180-day windows, hashed names | Additive |
| 202608 | `/adAccounts` adds `productType`, `originatingCustomer`; `/adCampaignGroups` adds billing/beneficiary/`buyingType` (rejected with 422 on earlier versions) | Additive. Response decoding ignores unknown fields; we send none of the new group fields |
| 202608 (all versions) | Legacy geo removed Aug 31, 2026: legacy geo targeting → 400 `INVALID_VALUE_FOR_FIELD` | None. Targeting accepts only Bing `urn:li:geo:<digits>` (`geoURNRE`), and the region table is Bing geo URNs |
| 202608 (all versions) | 1,000 DMP segments per account; `/v2/me` `location` removed | None. We read `adSegments`, never create segments; we do not call `/v2/me` |
| 202607 (all versions) | `creativeSelection` defaults to `OPTIMIZED` for `SPONSORED_INMAILS` + `LEAD_GENERATION` | None. Campaigns are `type: SPONSORED_UPDATES` |
| 202606 | Company Intelligence fields, Dynamic UTM `CREATIVE_NAME`, Message Ads "Not Interested" | Not used |
| 202605 | Events `endsAt` required; `memberCreatorPost(s)Analytics` `metricType` object → string | Not used (no Events API, no member post analytics) |
| 202605 | `adAnalytics` `appointmentsScheduled`; Conversions API `ownershipType` (defaults `OWNED`) | Additive; the conversions finder keeps its default behavior |
| 202604 | Member post metrics, Company Intelligence 180-day window | Not used |
| 202603 | Company Intelligence fields, Lead Sync webhook validation, `buyerGroups` targeting facet | Not used / additive |

Per-endpoint re-check against the li-lms-2026-10 pages:

- **Cursor pagination is unchanged.** `adAccounts` search (max `pageSize` 1,000), `adCampaigns`
  search (max 1,000) and the creatives `q=criteria` finder (max 100) all still page by
  `pageSize` + `pageToken` with `metadata.nextPageToken`, as `findByName`, the account walk,
  the monitor walk and the creative status cascade assume. Only the comments that said
  "at 202602" were reworded.
- **Offset finders** (`adSegments?q=accounts`, `conversions?q=account`) were written against
  li-lms-2026-10 in #552 and are untouched.
- **`adAnalytics` `q=analytics`**: `pivot=CAMPAIGN` and the `MEMBER_*` pivots, including
  `MEMBER_COUNTRY_V2`, are still documented; no metric this package requests is marked
  deprecated.
- **Campaign create body**: `politicalIntent` is still required (sent as `NOT_POLITICAL`); no
  new required field.
- **Not called at all**: `organizationAcls`, `adTargetingEntities`, `adPublisherRestrictions`,
  `/v2/me`. The targeting criteria from #552/#585 are validated locally and sent as URNs.

No code change beyond the version was needed.
