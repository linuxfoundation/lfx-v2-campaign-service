# 2026-08-24 — five defects in one memory model, and what they had in common

**Fix** — the Meta `/adimages` upload no longer copies the image. `multipartFraming` generates
the fixed prefix and suffix once with an empty part, and the request body becomes
prefix + image + suffix with the payload referenced in place.

**Measured, not derived**: uploading a 32 MiB image allocates **169,432 bytes — 0.50% of the
payload**. The previous buffered shape allocates **33,703,328 bytes — 100.4%**. A 199x reduction,
and `TestUploadImageDoesNotCopyTheImage` fails against the old shape at a budget of half the
payload.

## The pattern, which is the point of this entry

This was the fifth defect in one memory model across five rounds. Listed together, they are one
mistake wearing five costumes:

| round | defect | what was true |
| --- | --- | --- |
| 1 | aggregate charged AFTER the load | the bound ran after the allocation it accounted for |
| 2 | encoded base64 string stayed resident | an allocation nobody had counted |
| 3 | reservations leaked on failure arms | the bound was released on some paths, not all |
| 4 | leak on the panic path | an exit the guard's condition could not see |
| 5 | multipart copy outside the budget | an allocation nobody had counted |

Rounds 2 and 5 are the *same* defect: **a copy of the image existed that the bound did not know
about.** Rounds 1, 3 and 4 are also the same: **the bound existed but did not cover every path.**

So the recurring error is not carelessness about any one line. It is that each round reasoned
about the allocation it was changing and asserted the total in a comment, and a comment cannot
notice a copy elsewhere. Three consecutive rounds each falsified prose written in the round
before.

## What actually broke the cycle

**Enumerate the sites, then state the number — and put the enumeration in the code.**
`asset_admission.go` now lists every place an image is materialised on the dispatch path, with
the charge for each:

```
resolved asset slices   CHARGED (per distinct asset; variants alias one buffer)
multipart request body  ZERO — framed, not copied
per-attempt HTTP reader ZERO — bytes.NewReader is a view
uploadCache             ZERO — sha256 keys and hash strings, never bytes
```

A future copy has to be added to that list to be justified, which is a harder thing to do by
accident than adding an allocation and not updating a total.

**And measure rather than derive.** Every previous peak in this model was arithmetic in a
comment, and each was wrong in the round after it was written. `TotalAlloc` across a real upload
is not arithmetic: it counts what actually happened, including the copies nobody remembered.
`TotalAlloc` specifically — not `HeapAlloc` — because it only grows and so is immune to whether
the GC happened to run mid-measurement.

## The constraint that made streaming safe

The reason the copy existed at all was replay: an `io.Reader` is consumed by its send, so a
retry over a used reader posts a truncated body — Meta rejects it for a reason unrelated to the
throttle, and the failure is misdiagnosed. That is a WORSE defect than the memory it saves.

Framing keeps replay exactly: the three slices are immutable and a fresh `io.MultiReader` per
attempt copies nothing, because `bytes.NewReader` is a view. `TestUploadImageRetrySendsTheFullBody`
captures every attempt server-side and requires them byte-identical and to contain the whole
image — and it fails against a deliberately hoisted shared reader.

Two things the framing had to get right and did not get for free:

- **`ContentLength` must be set explicitly.** `net/http` infers it from a `*bytes.Reader` but not
  from an `io.MultiReader`; without it the upload goes out chunked, which `/adimages` is not
  documented to accept.
- **The framing must be byte-identical to the encoder's.** It is generated BY `mime/multipart`
  with an empty part rather than hand-assembled, and
  `TestMultipartFramingMatchesBufferedEncoding` asserts equality with the buffered encoding on the
  same boundary, then re-parses the result to prove both sides are not wrong together.

`GetBody` is not needed: this client's `CheckRedirect` is `noFollow`, so `net/http` never replays
the body itself.

## The rule

**A memory bound must enumerate what it covers, and the number must be measured.** If a bound
states a peak without listing the allocations behind it, the next allocation added anywhere on
the path silently falsifies it — and the failure is invisible until something is OOM-killed.
