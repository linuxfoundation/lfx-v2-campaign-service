# Implementation Plan: Meta single-image ad creative (uploadable)

**Branch**: `feat/meta-image-video-creatives` | **Date**: 2026-08-16 | **Spec**: [spec.md](./spec.md)

**Input**: Feature specification from `specs/004-meta-single-image-creative/spec.md`

## Summary

Add the ability to upload an image asset and have the Meta adapter build a real
single-image ad creative from it, instead of today's link/text-only creative. A new
synchronous upload endpoint stores image bytes in Postgres (`bytea`) and returns an
`asset_id`; the Meta per-variant config gains an optional reference to that asset; at
dispatch the Meta client uploads the bytes to the resolved ad account
(`POST /act_{id}/adimages`), obtains the account-scoped `image_hash`, and emits
`object_story_spec.link_data.image_hash`. The creative construction is refactored behind
a format-keyed builder so video and carousel can be added later without touching the
image path. Activation stays explicit (existing `toggle-campaign-status`); nothing is
auto-activated.

## Technical Context

**Language/Version**: Go (per `go.mod` — authoritative)

**Primary Dependencies**: Goa v3.25.3 (HTTP contract codegen), pgx/v5 (Postgres),
golang-migrate (embedded migrations), existing Meta Graph API client
(`internal/platform/meta`)

**Storage**: PostgreSQL. New `creative_assets` table with a `bytea` bytes column
(single-datastore model; no external object storage). Existing AES-256-GCM credential
encryption is unrelated and unchanged (image bytes are not secrets, stored plaintext).

**Testing**: `go test` (unit, no DB) for validation/creative-builder/idempotency logic;
`dbtest` integration suite (needs PostgreSQL 16 via `TEST_DATABASE_URL`) for the repo +
upload handler; Meta HTTP calls covered by the existing httptest-server pattern in
`internal/platform/meta/client_test.go`.

**Target Platform**: Linux server (Kubernetes, Helm chart under `charts/`)

**Project Type**: Web service (Go/Goa HTTP API); the front-end (`lfx-self-serve`) is a
separate repository and out of scope here.

**Constraints**: Backward compatible — the no-image path MUST be unchanged. Upload
endpoint validates before persisting. `/adimages` upload MUST be idempotent per
(ad account + content checksum). Generated code is authored only via `design/` + `make apigen`.

**Scale/Scope**: One new endpoint, one new table/migration, one new repo + service method,
edits to the Meta dispatcher and Meta client, plus OKF docs. Single-image only.

## Implementation approach (ordered, each an independently reviewable commit)

### C1 — API contract: upload endpoint + variant image reference (`design/`, then `make apigen`)
- Add a synchronous `POST /projects/{project_id}/briefs/{brief_id}/creative-assets` Method.
  - Payload: `bearer_token`, `project_id` (slug), `brief_id` (UUID), `content_type` (String,
    enum `image/png`,`image/jpeg`), and `bytes` (Goa `Bytes` — base64 in the JSON body).
  - Result: `CreativeAsset` (`asset_id`, `project_id`, `brief_id`, `mime_type`, `byte_size`,
    `checksum`, `created_at`), `201 Created`.
- Extend the documented `metaConfig.variants[]` shape with an optional `imageAssetId`
  (the `config` envelope is `Any`, so this is a doc/struct change, not a DSL type change).
- Run `make apigen`; commit `design/*.go` **and** regenerated `gen/**` together.
- **Transport decision (see research.md)**: base64 `Bytes` in a JSON payload (Goa-native,
  no multipart machinery; ~33% inflation is acceptable for feed-image sizes). Multipart via
  `MultipartRequest` is the rejected alternative — heavier, no precedent in this repo.

### C2 — Domain model + migration (`internal/domain/model`, `migrations/000026_*`)
- `CreativeAsset` domain struct mirroring the table.
- Migration `000026_create_creative_assets`:
  ```sql
  CREATE TABLE IF NOT EXISTS creative_assets (
      id           UUID        PRIMARY KEY DEFAULT gen_random_uuid(),
      project_id   UUID        NOT NULL,
      brief_id     UUID        NOT NULL REFERENCES campaign_briefs(id),
      mime_type    TEXT        NOT NULL CHECK (mime_type IN ('image/png','image/jpeg')),
      byte_size    BIGINT      NOT NULL,
      checksum     TEXT        NOT NULL,          -- sha256 of bytes, for dedupe/idempotency
      bytes        BYTEA       NOT NULL,
      created_by   JSONB,
      created_at   TIMESTAMPTZ NOT NULL DEFAULT now(),
      UNIQUE (brief_id, checksum)                 -- same image re-uploaded to a brief is one row
  );
  ```
  (down: `DROP TABLE creative_assets;`)

### C3 — Repo + upload handler (`internal/infrastructure/postgres/creative_asset_repo.go`, `internal/service/creative_asset.go`)
- Repo: `InsertAsset` (returns existing row on `(brief_id, checksum)` conflict — upload is
  itself idempotent), `GetAsset(assetID)` returning bytes + metadata.
- Handler validation (FR-002) **before** insert: MIME ∈ {png,jpeg}; decode + sniff actual
  content type (don't trust the declared header); byte size ≤ configured max; decode image
  header to check min dimensions / aspect for a single-image feed ad. Reject with a specific
  4xx; persist nothing on failure.
- Add a config value for max upload size (CLI flag → env → default), per the repo's config
  precedence.

### C4 — Dispatch wiring (`internal/dispatch/meta.go`)
- Extend `metaConfig` with `Variants[].ImageAssetID string`.
- After `resolveMetaCredentials` (account known), for each variant with an `imageAssetID`:
  load the asset bytes via the repo and attach them to the `meta.AdVariant` handed to the
  client. Missing asset → fail the dispatch with a clear "referenced asset not found" error
  (FR: no silent link-only fallback).

### C5 — Meta client: upload + creative builder (`internal/platform/meta/creative.go`, `client.go`)
- `uploadImage(ctx, accountID, bytes, checksum) (imageHash string, err error)` →
  `POST /act_{id}/adimages`. Idempotent: first consult a per-dispatch cache keyed by
  (accountID, checksum); the resolved hash is also persisted in the campaign `result` JSONB
  (C6) so a later reconcile/retry reuses it rather than re-uploading.
- Introduce `creativeSpecBuilder` keyed by creative type. `imageLinkDataBuilder` produces
  `link_data` with `image_hash` + existing message/name/description/CTA. `createVariantAd`
  calls the builder instead of hand-building `link_data`. Video/carousel builders are the
  planned future implementations of the same interface (FR-007 / SC-005) — not built now.
- No-image variant → the builder returns today's link-only `link_data` (backward compatible).

### C6 — Persist resolved hash + degraded semantics (`client.go` result, dispatch mapping)
- Record `{account_id → image_hash}` (or per-variant) in the campaign `result` JSONB.
- If `/adimages` or the creative/ad create fails after the campaign/ad set exist upstream,
  return the campaign with an error so the orchestrator retains it as `created_degraded`
  (existing `preservableErrorStatuses` path) — never reported as clean success.

### C7 — Tests
- Unit (no DB): validation matrix (good png/jpeg, bad MIME, oversize, under-dimension);
  creative-builder output for image vs no-image; `uploadImage` idempotency via httptest
  server asserting exactly one `/adimages` POST per (account, checksum).
- Integration (PG16 dbtest): upload handler round-trip; repo insert/get + `(brief_id,checksum)`
  conflict returns existing; dispatch loads bytes and produces an `image_hash` creative
  against a stubbed Meta server.

### C8 — OKF knowledge base (required for CI `validate-okf`)
- Update `docs/knowledge/code/internal-platform-meta.md` (creative is no longer link-only;
  document the builder + `/adimages` idempotency) and its `docs/knowledge/code/index.md`
  bullet **verbatim**.
- Update the Meta section of `docs/api-catalog.md` (new upload endpoint; `imageAssetId`).
- Add `docs/knowledge/log/2026-08-16-<ticket>-meta-single-image-creative.md`
  (`**Creation**` marker).
- `go run ./cmd/okfvalidate ./docs/knowledge` MUST pass. Do **not** run `okfgen`.
